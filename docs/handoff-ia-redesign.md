# 개발 요청 — 정보 구조·화면 재구성 구현

## 요청

`docs/superpowers/specs/2026-09-03-information-architecture-redesign.md`(이하 기획서)를 구현한다.
기능을 추가하는 작업이 아니라 **있는 기능을 사용자가 예상하는 자리로 옮기고, 한 화면이 한 질문에 답하게 만드는 작업**이다.

Swiss Ledger 시각 언어 적용은 이미 main에 머지되어 있다(`1673dd2`, `87ad9c2` 등). 이 작업은 그 위에서 **구조**를 바꾼다.

## 읽는 순서 (셋 다 읽어야 한다)

문서가 셋이고 역할이 다르다. 하나만 읽고 진행하면 어긋난다.

1. **기획서** `docs/superpowers/specs/2026-09-03-information-architecture-redesign.md` — 구조 정본. 메뉴, 화면 역할, 기능 재배치표(§9), 7단계(§12), 완료 조건(§13).
2. **홈** `docs/handoff-dashboard-v2.md` + `docs/design/swiss-ledger/dashboard-v2.html` — 홈 화면의 내용·데이터 정본. 기획서 §7.1은 이 목업을 따른다. 신규 쿼리 4개가 여기 정의되어 있다.
3. **시각** `docs/design/swiss-ledger/foundation.html` + `docs/handoff-ui-redesign.md` — 색·타이포·컴포넌트 정본. 새로 만드는 화면 요소는 전부 이 규칙을 따른다.

충돌하면 기획서 머리말의 역할 분담대로 해당 정본을 따른다.

## 이미 내려진 결정 (다시 논의하지 않는다)

기획서를 두 사람이 검토해 아래를 확정했다. 구현 중 "이게 맞나" 싶어도 문서대로 간다.

- 상위 메뉴 6개: **홈 · 거래 · 가져오기 · 예산 · 분석 · 자산**, 설정은 우측 아이콘. 모바일 하단 5개(홈·거래·가져오기·예산·더보기).
- **홈은 이번 달 고정.** 월 이동 없음. 연도 축은 분석 > 연간에만 존재한다 (§5.7).
- 거래 화면 상단의 남은 돈·월말 예측·월 KPI·경고 배너는 **홈으로 이관**한다. 거래는 원장만 남는다.
- **"남은 돈"은 앱 전체에서 한 가지 정의**: 저축 목표 기반 지출 상한(월평균수입 × (1 − 목표저축률)) 기준. 예산 합계 기준 잔액을 나란히 두지 않는다.
- 분석 탭은 **4개**(요약·카테고리·가맹점·연간). 추이 탭은 없다. 항목별 월별 표가 카테고리 탭의 중심이다.
- 예산은 **한 화면**: 카테고리 행이 곧 입력칸. 시뮬레이터만 기본 접힘.
- 가져오기의 "처리 기록"은 **1차에서 `(source, created_at 날짜)` 근사 그룹핑**. 스키마 추가 없음.
- 자산의 주 경로는 뱅샐 자동 스냅샷이고 수동 입력은 "잔고 보정"이다.
- 항목별 상세(`/category`)와 월말 리뷰는 상위 메뉴에서 빠지고 문맥 진입만 남는다.
- URL은 1차에서 유지. 바꿀 때는 항상 리디렉션과 함께.

## 시작 전 두 가지

1. **기획서를 먼저 커밋한다.** 지금 untracked 상태다. 다른 문서들은 커밋되어 있다.
2. 이 저장소는 다른 세션이 동시에 작업할 수 있다. 시작 전에 `git status`로 미커밋 변경을 확인하고, 있으면 그 파일은 건드리지 말고 진행하거나 먼저 정리되길 기다린다. 인박스 관련 파일(`src/features/inbox/*`)이 자주 편집된다.

## 단계와 커밋

기획서 §12의 7단계를 그대로 따른다. **단계마다 커밋**하고, 각 커밋에서 `pnpm lint` · `pnpm exec tsc --noEmit` · `pnpm test` · `pnpm build`가 전부 통과해야 한다.

### 1단계 — 내비게이션과 용어
- `src/components/app-header-menu.tsx`: 상위 6개 + 설정 아이콘. `항목별 상세`, `연간결산`, 설정의 `가져오기` 앵커 링크 제거.
- 모바일 메뉴를 5개 하단 구조로. `더보기`에 분석·자산·설정을 그룹으로.
- 용어: 대시보드→홈, 가계부→거래, 인박스→가져오기, 고정비용→정기거래, 항목→카테고리. **화면명과 메뉴 라벨만** 바꾸고 라우트는 유지.
- `HeaderSection` 타입과 각 페이지의 `active` 값을 새 섹션 기준으로 정리.

### 2단계 — 홈 = 이번 달 조종석, 거래 = 원장 (핵심)
- `handoff-dashboard-v2.md`의 신규 쿼리 4개를 먼저 만들고 테스트를 쓴다: `getNetWorthSeries`, 고정비/변동비 분해, 적정 페이스 기준선, `getHomeTodos`.
- 홈을 `dashboard-v2.html` 구성으로 구현. 연도 선택기와 연 누적 KPI, 전체 상세표는 홈에서 제거.
- 거래에서 상단 조종석 블록을 제거하고 요약 바를 "필터 결과 합계"로 바꾼다. `forecast.ts`, safe-to-spend 계산은 이미 feature 모듈에 있으니 렌더 위치만 옮긴다.
- 정기거래 "이번 달 반영" 상태와 버튼을 거래에 추가.
- **여기서 멈추고 실물을 확인한다.** 1~2단계로 체감의 대부분이 끝나고, 3단계 이후는 실물을 보고 조정할 수 있다.

### 3단계 — 가져오기 작업 공간
- 탭 4개: 검토 대기[N] · 파일 업로드 · 처리 기록 · 미분류 거래[N]. 탭 상태는 URL에.
- 기본 탭 규칙: 대기가 있으면 검토 대기, 없으면 업로드.
- 미분류 거래는 `/manage?tab=unclassified`의 `BulkClassifyForm`을 옮겨 재사용. 기존 주소는 리디렉션.
- 처리 기록은 근사 그룹핑. 한계(같은 날 같은 소스가 합쳐짐)를 화면에 한 줄로 명시.

### 4단계 — 예산
- 카테고리 행에 예산 입력칸 통합, 변경 시에만 저장 강조.
- "남은 돈"을 홈과 같은 정의로. 시뮬레이터는 접힘.
- 월말 리뷰 진입 조건 정리.

### 5단계 — 분석
- 탭 4개. `report.ts`를 연간 탭으로 흡수, `/report`는 `/analysis?view=annual`로 리디렉션.
- 항목별 월별 표(`category-detail-table.tsx`)를 카테고리 탭 중심으로 이동. 셀 클릭 제외·호버 툴팁 동작 보존.
- `/category`는 문맥 진입만. 상단에 분석으로 돌아가는 링크.

### 6단계 — 설정
- 결제수단 · 카테고리 · 가져오기 규칙(가맹점 사전+별칭) · 정기거래 규칙 · 자산 계정 · 계정 및 보안. 데스크톱은 좌측 로컬 내비.
- `/recurring`은 규칙 편집만 남기고 월 반영은 거래로.
- 자산 계정 추가·이름 변경을 자산 화면에서 설정으로.

### 7단계 — 반응형·일관성
- 콘텐츠 폭 규칙(§8.3), 모바일 하단 내비, 큰 표의 모바일 편집 방식.

## 지켜야 할 것

- **계산식 변경 금지**: 저축률, 예산 페이스, 예측, 자산 계산, 지문·분류 로직 (§14). 시각·구조 작업이니 계산 관련 테스트가 깨지면 잘못 건드린 것이다.
- 기존 테스트 전부 통과. 새 쿼리는 새 테스트(캐리포워드, 스냅샷 없는 달, 자산 미입력, 부채만 있는 경우, 할 일 우선순위).
- 모든 Drizzle 쿼리에 householdId 필터.
- URL을 바꾸면 반드시 리디렉션. 화면 간 내부 링크도 같이 갱신.
- 넓은 표는 `overflow-x-auto` 안에. 페이지 본문 가로 스크롤 금지.
- 기존 aria-label·sr-only 유지. 탭 컴포넌트는 키보드로 이동 가능해야 한다.
- 빈 상태(§13): 데이터 없을 때 빈 표나 0 카드를 그리지 않고 안내와 진입 버튼을 보인다.
- 파이·도넛 차트 금지, 이중 y축 금지, 모든 수치에 기준점.

## 완료 조건

기획서 §13 전체. 특히:
- 상위 메뉴 데스크톱 6개, 모바일 5개 이하. 같은 목적지로 가는 중복 메뉴 없음.
- 거래 화면 상단에 남은 돈·월말 예측·월 KPI 블록이 없다.
- 연도 기준 수치는 분석 > 연간에만 나타난다.
- "남은 돈" 정의가 앱 전체에서 하나다.
- 홈은 전체 카테고리 상세표를 초기 조회하지 않는다.
- 새 파일 업로드 후 3개 화면 이내에서 거래 반영이 끝난다.

## 환경

- `pnpm install` 후 로컬 Supabase(Docker) 필요. `.env.local`에 `DATABASE_URL`, `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY` 4개 (`.env.example` 참고). 없으면 테스트 파일 대부분이 실행되지 않는다.
- `SUPABASE_SERVICE_ROLE_KEY`는 로컬·테스트 전용. Vercel에 넣지 않는다.
