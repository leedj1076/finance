# 통합 예산 화면과 로컬 AI 예산 추천

작성일: 2026-09-10
코드 확인 기준: `main` / `275442c`
상태: 2026-09-10 사용자 문서 승인 완료. 구현 계획 작성 단계이며 구현·운영 DB 반영·배포는 아직 하지 않는다.

추가 요청: 설정의 공통·내역·예산 프롬프트 편집 방향도 승인되었다. 상세 계약은 `docs/superpowers/specs/2026-09-10-ai-diagnosis-settings-design.md`에서 관리한다. 해당 문서 확인 후 기존 실행 계획에 통합하며, 프롬프트 설정/호환성 관련 사항은 그 확장 명세를 함께 읽는다.

## 1. 목적과 승인된 원칙

예산 화면은 “선택한 달에 항목별로 얼마를 쓸까?”에 답한다.

- `/budgets`와 `/budgets/review`를 `/budgets` 하나로 통합한다.
- 지난달 예산·평균을 가져오는 기존 방법에 AI 예산 추천을 추가한다.
- AI는 추천 금액뿐 아니라 유지·증액·감액의 이유, 예외 지출 후보, 절감할 수 있는 부분과 근거를 제시한다.
- 사용자가 이번 달 특이사항을 선택적으로 입력할 수 있다.
- AI 결과는 제안이다. 선택한 항목을 편집안에 가져오고 사용자가 수정·저장해야 예산에 반영된다.
- 기존처럼 Mac의 Codex CLI 워커로 실행한다. Mac이 실행을 맡는 구조이지 오프라인 로컬 모델을 새로 설치하는 작업은 아니다.
- 설정된 저축 목표의 지출 상한을 우선한다. 이미 쓴 돈·확정 지출 때문에 어렵다면 목표를 임의로 낮추거나 불가능한 예산을 제안하지 않는다.
- 목표를 초과하는 현실적인 계획은 초과액·예상 순저축률·추가 조정 후보를 설명한다.
- 월중 실행도 “이미 쓴 금액 + 앞으로 쓸 금액”인 월 전체 예산을 제안한다. 남은 기간 배정액은 별도로 표시한다.

예산 반영은 거래 추가·분류 변경·월 마감과 무관하다. AI가 이 작업들을 대신 수행하지 않는다.

## 2. 현재 구조와 통합 범위

현재 두 화면 모두 `budgets(household_id, major, month)`에 저장한다.

- `src/app/budgets/page.tsx`: 선택 월 실제 지출·목표 상한·페이스 경고, 직접 편집, 지난달 예산/월평균 채우기, 감축 시뮬레이터.
- `src/app/budgets/review/page.tsx`: 대상 월 직전 달의 실적 비교, 고정비/비정기 예산 유지, 변동비 6개월 중앙값 제안, 절감률 일괄 적용.
- 두 화면의 기준 수입 산출 기간은 현재 다르다. 통합 시 상한을 두 종류로 표시하지 않는다. 기존 `/budgets`의 기준 수입·상한·반올림을 정본으로 사용한다.
- 기존 내역 진단은 `src/features/diagnosis/`의 스냅샷·작업 큐·워커·검증된 보고서 구조다. 예산 금액과 예정 지출은 별도 계약이 필요하므로 기존 `DiagnosisReport`에 억지로 넣지 않는다.

다음 기능은 유지한다: 직접 입력, 지난달 예산/월평균 채우기, 고정비·변동비·비정기 구분, 지난달 예산과 실적 비교, 6개월 중앙값 참고 및 채우기, 변동비 감축 도구, 예산 대비 실제·페이스 경고, 수동 저축 목표 변경.

## 3. 접근 방식 비교와 선택

1. **별도 AI 보고서를 읽고 예산 화면에 옮겨 적기**: 보고서는 독립적이지만 근거와 편집 금액 사이를 왕복해야 한다.
2. **같은 예산 편집표에서 AI 추천을 검토하고 선택 적용 — 선택**: 기존 금액·추천 금액·이유를 나란히 비교하며 한 번만 저장한다. 추천 작업의 수명과 편집 중인 값은 분리한다.
3. **AI 완료 즉시 저장하고 되돌리기 제공**: 조작은 적지만 기존 편집값을 덮어쓰고 사용자 확인 전에 예산이 바뀐다. 승인된 확인 후 반영 원칙과 맞지 않아 채택하지 않는다.

이하 세부사항은 선택한 방식의 구현 계약이며, 이 문서 검토에서 최종 확정한다.

## 4. 통합 화면

### 4.1 대상 월과 상단 요약

- URL은 `/budgets?month=YYYY-MM`. 월 선택기는 하나이며 표·추천·상단 요약이 같은 대상 월을 가리킨다.
- 기존 직접 편집·월 선택 범위는 유지한다. AI 신규 추천은 1차 버전에서 이번 달과 다음 달을 지원한다. 과거 월의 기존 추천은 조회할 수 있으나 사후 목표를 맞추기 위한 신규 추천은 만들지 않는다.
- 다음 달 예산 만들기는 다음 달의 동일 화면으로 이동한다.
- 상단은 기준 수입·저축 목표·목표 지출 상한·편집안 합계·상한 대비 여유/초과를 보여준다. 기준 수입은 예상 수입의 참고값이며 실제 잔액으로 표현하지 않는다.
- 이번 달에는 이미 쓴 금액과 앞으로 배정한 금액을 함께 보여준다. 미래 월에는 소비 페이스 경고를 표시하지 않는다.
- 기존 마감 상태 표시는 유지하되, 예산 저장을 월 마감 동작으로 오인하게 하지 않는다.

### 4.2 지난달 돌아보기와 초안 만들기

- 지난달 수입·지출·순저축률·예산 초과 요약은 접을 수 있는 참고 영역으로 합친다. 별도 편집표는 만들지 않는다.
- 채우기 도구: 지난달 예산, 기존 월평균, 기존 리뷰 규칙 추천, AI 예산 추천.
- 기본 화면에서 모든 참고 열을 늘어놓지 않는다. 지난달 비교·중앙값·감축 도구는 필요할 때 펼친다. AI 없이도 기존 편집을 완료할 수 있어야 한다.
- 어떤 채우기 도구도 즉시 DB에 저장하지 않는다. 수정 중인 행을 바꾸려면 대상 행과 변경 내용을 미리 보여준다.

### 4.3 AI 실행 입력

- 대상 월과 기준 수입·저축 목표·지출 상한을 실행 전에 보여준다. AI는 목표를 변경할 수 없다.
- 특이사항은 선택 입력이다. 예: “이번 달 여행 없음”, “지난달 가전 구매는 일회성”, “생일 선물 예산 필요”.
- 금액을 반드시 확보할 예정 지출은 선택형 목록으로 분리한다: 대분류, 미지출 금액, 설명. 자유문장에서 AI가 추출한 금액을 자동으로 확정 금액에 더하지 않는다.
- 이 목록은 “아직 거래에 없고 정기거래에도 없는 추가 예정 지출”임을 명시한다. 정기거래와 겹치거나 이미 지출한 항목은 사용자가 확인·정리한다.
- 사용자가 입력한 정보는 사용자 제공 정보로 표시하고, 거래로 증명된 사실과 구분한다. 입력은 추천 작업의 스냅샷에 보관하며 계좌번호·파일·자격 증명을 추가로 요구하지 않는다.
- 초기 제한: 특이사항 4,000자, 추가 예정 지출 30건 이하, 항목 설명 200자 이하. 금액은 기존 예산 파서의 정수·범위 규칙을 따른다.
- 저장하지 않은 저축 목표 변경은 먼저 기존 저장 절차로 확정한다. 추천 시작만으로 전역 설정을 바꾸지 않는다. 저장하지 않은 예산 편집안은 참고 입력으로 전달하되, 해당 금액이 미저장 초안임을 스냅샷에 표시한다.

### 4.4 한 편집표에서 검토

대분류마다 기존 저장 예산, 현재 편집 금액, AI 추천 금액, 짧은 추천 이유를 제공한다. 예산 저장 단위는 기존처럼 대분류이고 분석 근거는 소분류·가맹점·거래까지 내려간다.

- “왜 이 금액인가”를 펼치면 최근 추이, 예외 지출 후보, 유지할 비용, 조정 후보와 근거 거래를 보여준다.
- 확인되지 않은 일회성 지출은 “일회성으로 추정” 또는 “확인 필요”로 표시한다. 거래를 통계에서 제외하거나 삭제하지 않는다.
- 예산이 줄어든 이유가 절약인지 지난달 일회성 비용의 소멸인지 구분한다. 비정기 실제 지출 감소를 월 적립 예산 폐지로 해석하지 않는다.
- 처음에는 아무 항목도 선택하지 않는다. 개별 선택·전체 선택·선택한 추천 가져오기를 제공한다.
- 추천 가져오기는 선택 행의 편집 금액만 바꾼다. 선택하지 않은 행·수동 입력·스크롤·펼침 상태는 유지한다.
- 일부 항목만 가져온 경우 상단 합계·예상 저축률은 실제 혼합 편집안으로 다시 계산한다. 전체 AI 제안의 합계와 혼동하지 않게 한다.
- 추천 금액을 사용자가 수정할 수 있다. “AI 추천 A원 → 사용자 조정 B원”을 구분하며 AI가 B원을 추천했다고 표시하지 않는다.
- 적용 전까지 되돌리기는 편집안에 한정한다. 실제 저장의 완료 여부와 별개로 표시한다.

## 5. 분석 입력과 계산 계약

### 5.1 입력 스냅샷

서버가 가구 범위로 다음을 읽고, 요청 시점의 불변 스냅샷을 만든다.

- 대상 월·한국 시간 기준 조회 시점, 기존 기준 수입·저축 목표·목표 상한 및 각각의 산출 기간.
- 대상 월 전체 거래: 부호를 보존한 지출, 환불, 수입, 저축 납입을 구분한다. 저축 납입을 지출에 이중 계상하지 않는다.
- 대상 월의 대분류별 실적·저장 예산·사용자 편집안.
- 대상 월 이전 최근 6개월의 대분류/소분류 추이, 거래 근거, 전월 비교, 월별 마감 상태와 기록 존재 여부. 아직 끝나지 않은 이전 달을 참고할 때는 부분 월이라고 명시한다.
- 정기거래의 대상 월 발생 여부·납부 일정·미반영 여부, 비정기 적립 구분, 사용자 특이사항과 추가 예정 지출.
- 미분류·검토 대기 등 기록의 불완전성을 알리는 개수. 인박스 항목은 실제 지출로 합산하지 않는다.

새 AI 분석에서는 마감 월을 확정된 비교 근거로 우선하고 미마감 월은 잠정 자료로 표시한다. 기존 월평균 채우기·리뷰 중앙값의 계산식은 바꾸지 않는다. 자료가 없는 달을 자동으로 0원 지출 달로 해석하지 않는다.

전체 금액 집계는 모든 범위 내 거래로 계산한다. 모델 입력 한도를 넘으면 집계는 유지하고 거래 근거 목록만 제한하며 전체/제공 거래 수를 명시한다. 제공하지 않은 거래를 근거로 인용할 수 없다. 1차 한도는 근거 2,000건, 직렬화한 스냅샷 1MiB이며, 큰 거래와 최근 거래를 결정적인 순서로 선택한다. 집계 자체가 한도를 넘으면 불완전한 추천 대신 입력 과다 안내로 중단한다.

### 5.2 돈 계산은 서버가 담당

- 수입 기준·저축률·목표 상한·기존 페이스 계산은 기존 함수를 재사용한다. AI는 새로운 “남은 돈” 공식을 만들지 않는다.
- 추천 총액·추천 후 예상 순저축률·목표 초과액·항목별 남은 배정액은 AI 응답의 숫자를 신뢰해 표시하지 않고 서버가 재계산한다.
- 이미 쓴 금액은 환불을 포함한 순지출이다. 월 전체 예산에서 이를 뺀 값은 “앞으로 배정한 금액”이며 계좌 잔액으로 부르지 않는다.
- 항목별 추천 하한은 0원과 “기록된 순지출 + 미반영 정기 지출 + 사용자가 명시한 추가 예정 지출” 중 큰 값이다. 모델이 하한 미만을 반환하면 검증 실패로 처리하고 금액만 조용히 보정해 이유와 숫자를 어긋나게 만들지 않는다.
- 정기 지출은 기존 발생 월·종료월·회차·영업일·반영 식별 규칙을 사용한다. 이미 반영된 정기거래를 다시 더하지 않는다. 수동 입력과의 불확실한 일치 등은 가정/확인 필요 사항으로 드러낸다.
- 카테고리가 없거나 숨겨진 지출도 전체 지출에서는 빠뜨리지 않는다. 해당 금액은 미배분 기지출로 표시하여 전체 제안의 상한 대비 평가에 포함하고, 정상 대분류 예산인 것처럼 저장하지 않는다.
- 기준 수입이 없으면 AI가 수입을 추정해 목표 상한을 만들지 않는다. 현재 화면의 기준값을 설명하고 AI 추천 생성은 막으며 수동 편집은 유지한다.
- 합계가 상한을 넘는 결과도 유효한 제안일 수 있다. 초과 사유와 추가 조정 방향을 필수로 제시하고, 저장 시 사용자가 초과를 확인하도록 한다. 저축 목표는 그대로 유지한다.

## 6. 결과 계약과 근거 검증

예산 전용 `BudgetRecommendationSnapshot` / `BudgetRecommendationReport`를 만든다. 기존 내역 진단 타입과 구분한다.

보고서는 전체 요약, 데이터 한계·가정, 대분류별 추천을 가진다. 항목별 필수 내용은 다음과 같다.

- 대분류 식별값과 월 전체 추천 금액.
- 유지·증액·감액의 이유.
- 일회성 후보와 절감 가능성: 없으면 빈 목록을 반환한다. 없는 근거를 만들지 않는다.
- 스냅샷에 실제 존재하는 거래 ID·정기거래 ID·사용자 입력 항목 참조.
- 사용자 입력을 인용하는 경우 원문에 대응하는 짧은 근거와 사용자 제공 정보 표시.
- AI 설정의 공통/예산 지침을 근거로 삼는 경우 요청 당시 `prompt_input`의 영역과 원문 인용을 참조하고 사용자 제공 정보로 표시한다. 작업 당시 지침에 실제 존재하는 문구인지 검증하며 현재 설정으로 대체하지 않는다.

금액은 유한한 0 이상의 원 단위 정수로 기존 저장 가능 범위 안에 있어야 한다. 각 활성 지출 대분류는 정확히 한 번 나와야 하며, 누락·중복·다른 가구 항목·존재하지 않는 근거는 검증 실패다.

검증은 로컬 결과 수신 시와 서버 저장/조회 시 양쪽에서 수행한다. 합계 일치, 하한, 상한 초과 사유, 허용된 참조를 확인한다. 문장 자체가 맞다는 보장은 하지 않으며, 추정과 확인 가능한 사실을 구별하여 보여준다.

## 7. 실행 구조와 상태

### 7.1 공유할 것과 분리할 것

- 공유: 기존 Mac 실행 서비스, 워커 인증, Codex 실행의 격리·시간 제한·출력 제한·도구 차단, heartbeat/lease 처리 방식.
- 분리: 예산 스냅샷·프롬프트·결과 스키마, `/api/budget-recommendations`, 예산 작업 큐와 RPC.
- 기존 `diagnosis_jobs`의 금융 스냅샷/결과 계약은 유지한다. 예산용 `budget_recommendation_jobs`를 추가하고 기존 워커 등록에 연결한다. 프롬프트 설정 확장에 따라 별도 불변 `prompt_input`을 보관하고, 기존 claim RPC의 인자/legacy 반환은 유지하되 새 지침 작업은 구형 워커가 가져가지 못하도록 선택 조건을 제한한다. 구체적인 호환 경계는 AI 설정 확장 명세 §7을 따른다.
- Mac 프로세스 하나가 내역 진단과 예산 추천을 번갈아 확인하며 한 번에 한 작업을 실행한다. 한 종류의 요청이 계속 들어와 다른 종류가 굶지 않게 한다.
- 공통 실행 코드는 프롬프트·스키마·검증기를 인자로 받는 작은 공용 실행부까지만 추출한다. 범용 이벤트 버스나 플러그인 프레임워크는 만들지 않는다.

### 7.2 내구성과 사용자 표시

- 상태는 기존처럼 `queued`, `running`, `completed`, `failed`를 사용한다. 가구·대상 월당 활성 예산 추천은 하나만 허용한다.
- 작업 생성은 같은 요청의 재시도에 멱등하다. 사용자의 명시적인 재추천은 완료 작업 이후 새 작업을 만든다.
- 입력 읽기·스냅샷 저장은 일관된 시점으로 묶는다. fingerprint는 거래, 예산, 카테고리 메타, 정기 규칙/반영 여부, 마감 상태, 목표, 특이사항, 예정 지출, 참고 편집안의 실질 변경을 포함한다. 매 조회 시각만 달라져도 stale이 되지는 않는다.
- 분석 자료의 변경 여부와 편집안/저장 예산의 변경 여부를 별도로 비교한다. 요청 당시 참고 편집안은 불변 입력으로 남기되, 결과를 가져온 뒤 사용자가 금액을 조정했다고 자동으로 재추천을 강제하지 않는다. 한국 날짜 경과로 남은 기간 등 실제 분석 조건이 달라지면 갱신을 안내한다.
- 요청 당시 공통/예산 지침과 프롬프트 버전을 작업에 보존한다. 지침 변경 알림은 금융 자료 변경과 분리하며, 지침 수정만으로 이전 추천·저장 예산을 무효화하지 않는다. 새 지침은 새 요청부터 사용한다.
- 화면은 Mac 연결 대기 → 분석 중 → 결과 검증/완료를 실제 확인 가능한 상태까지만 표시한다. 알 수 없는 백분율 진행률은 만들지 않는다.
- 페이지를 나가도 작업은 서버 큐에 남으며 돌아오면 상태를 복구한다. 월 전환 시 이전 월의 polling과 늦은 응답을 무시한다.
- Mac이 꺼졌거나 워커 버전이 예산 기능을 지원하지 않으면 이유와 연결/업데이트 안내를 제공한다. 전체 화면 로딩으로 기존 예산 편집을 막지 않는다.
- 재추천 중에도 이전 결과와 편집안은 보존한다. 새 결과가 와도 자동으로 행 선택·금액 덮어쓰기를 하지 않는다.
- 실패·연결 지연·lease 만료에는 재시도할 수 있고, 검증되지 않은 결과는 적용할 수 없다.

## 8. 저장과 오래된 추천 보호

- AI 추천 가져오기와 DB 저장을 구분한다. 저장은 기존 “변경사항 저장” 경로 하나로 통합한다.
- 서버는 현재 가구, 대상 월, 허용 대분류, 적용할 작업의 완료 상태·가구·대상 월·추천 행을 확인한다. 클라이언트가 보낸 이유 문장을 DB의 권위 있는 근거로 신뢰하지 않는다.
- 저장 시 변경 행만 저장하고, 편집 시작 시점의 예산 값과 현재 DB 값을 비교한다. 다른 창/배우자가 변경했으면 충돌 안내 후 비교·새로고침하도록 하며 조용히 덮어쓰지 않는다. 모든 예산 저장 진입점은 동일한 충돌 검사와 트랜잭션을 사용한다.
- 추천을 가져올 때와 저장할 때 현재 입력을 다시 검사한다. 추천 생성 후 거래·목표·정기 규칙 등 분석 자료가 바뀌었다면 “기록 변경 후 재추천 필요”를 표시하고 해당 추천의 AI 적용은 막는다. 수동 편집은 가능하다.
- 추천과 사용자의 편집은 구분한다. 결과를 가져온 뒤 행을 수정하는 것은 허용된 조정이며 그 자체로 추천의 근거 거래가 오래됐다는 뜻은 아니다.
- 예산 행에 선택적으로 추천 작업 ID를 저장한다. 이유와 원래 추천 금액은 그 불변 작업 결과에서 읽는다. 저장액과 추천액이 다르면 사용자 조정으로 표시한다. 관련 참조는 DB에서도 완료 작업의 가구·월·대분류 일치를 검증한다.
- 추천을 가져온 뒤 금액을 수정하는 동작은 AI 유래 사용자 조정으로 출처를 유지한다. 지난달/평균 채우기나 “수동 초안으로 전환”으로 명시적으로 대체한 행에는 이전 AI 출처를 붙이지 않는다. 변경하지 않은 다른 행의 출처는 유지한다. 이유가 사라지지 않도록 예산에서 참조 중인 완료 작업은 자동 삭제하지 않는다.
- 자기 추천을 저장한 결과는 “적용됨”으로 표시하며 저장 직후 근거 거래가 변경됐다는 경고를 띄우지 않는다. 반영 이후의 타 사용자/다른 저장 변경은 충돌 검사의 새로운 기준으로 삼고, 같은 과거 결과를 묵시적으로 반복 적용하지 않는다.
- AI 저장 경로는 저축 목표를 바꾸지 않는다. 기존 수동 목표 변경은 별도 명시 동작으로 유지하며, 목표 변경 시 이전 추천은 재평가 대상이 된다.
- 금액과 출처 저장은 원자적이며 중복 제출이 새 거래·중복 예산을 만들지 않는다. 저장 후 관련 화면 캐시만 무효화하고 현재 편집 화면의 스크롤·확장 상태를 유지한다.

## 9. 보안·격리·호환성

- 모든 조회와 저장에 인증된 `householdId` 조건을 적용한다. 새 테이블은 RLS를 켜고 가구 구성원의 자기 가구 결과 조회만 허용한다.
- 브라우저에 워커 토큰·서비스 키를 전달하지 않는다. 큐 생성/결과 완료/취소 등 권한은 기존 서버·RPC 경계를 따른다. 원시 테이블의 임의 INSERT/UPDATE로 결과나 작성자를 위조하지 못하게 한다.
- 워커 결과 쓰기는 해당 가구의 유효한 워커·작업·claim token·lease를 모두 검사한다. 사용자에게 보여줄 완료 결과는 서버가 다시 검증한다.
- 자유문장과 거래 적요는 신뢰할 수 없는 데이터다. 모델 도구·웹 검색·임의 파일 접근을 허용하지 않는다. 결과는 HTML 실행 없이 렌더링한다.
- 로그에 거래 본문·사용자 특이사항·프롬프트·토큰을 기록하지 않는다. 작업 ID·상태·안전한 오류 코드만 남긴다.
- `/budgets/review?month=M`은 대상 월 M을 유지해 `/budgets?month=M`으로 리디렉션한다. 파라미터가 없으면 기존 review의 기본값인 한국 시간 이번 달을 사용한다. `reviewSaved=1` 등 기존 저장 복귀 URL도 새 화면에서 깨지지 않게 처리한다.
- 홈·내역 등에서 review로 가는 내부 링크와 캐시 무효화 참조는 통합 화면으로 옮긴다. 외부 즐겨찾기를 위한 리디렉션은 유지한다.
- 기존 월 마감 서비스·트리거, 거래 import 지문, 분류 규칙, 저축률/자산/페이스 계산은 바꾸지 않는다.

## 10. UI 품질

- Swiss Ledger 토큰·타이포·다크모드를 유지한다. 넓은 표 두 개를 겹쳐 넣지 않는다.
- 모바일에서는 대분류별 카드/접힘 상세로 기존 금액·편집 금액·추천액과 선택 동작을 읽을 수 있게 한다. 페이지 전체 가로 스크롤을 만들지 않는다.
- 설명은 hover 전용으로 숨기지 않고 클릭/키보드로 펼칠 수 있게 한다. 근거 팝업은 화면을 벗어나지 않고 Escape로 닫힌다.
- 저장/추천 처리 상태는 `aria-live`로 알리고, 행별 수정·선택 때문에 전체 UI가 깜빡이지 않게 한다.
- 월별 상태는 월을 포함한 식별자를 사용하되 같은 부모의 서로 다른 패널 key는 이름 공간을 분리한다. 월 전환 시 이전 추천/마감 패널이 누적되지 않아야 한다.

## 11. 검증 기준

기존 테스트를 유지하고 새 기능은 실패 테스트부터 작성한다.

- 계산/스냅샷: 기존 상한과 일치, 환불 부호, 저축 납입 이중계상 없음, 월중 기지출, 정기거래 중복 방지·종료월·영업일, 추가 예정 지출, 미분류 포함, 자료 없는 달과 마감 0원 구별, 근거 제한에도 전체 합계 유지.
- 결과 검증: 누락/중복 카테고리, 음수·소수·과대 금액, 하한 미달, 타 가구/없는 근거, 초과 사유 없는 결과, 조작한 클라이언트 이유 거부.
- 저장: 선택하지 않은 예산 보존, 직접 조정과 AI 출처 표시, 중복 제출, 추천 이후 거래 변경, 다른 창에서 예산 변경, 전역 목표 변경 감지, 원자적 저장, 가구 격리.
- 큐/워커: 두 작업 종류의 격리와 공정한 처리, 활성 작업 중복 방지, 재추천, 토큰/lease/heartbeat 검증, Mac 오프라인·타임아웃·잘못된 출력, 기존 내역 진단 회귀.
- E2E: 과거 review URL의 대상 월 보존, 단일 편집표, 특이사항/예정 지출 입력, 완료 후에도 자동 적용 없음, 개별/일괄 선택·수정·저장·이유 재조회, 월/탭 이동, 늦은 응답, 실패 후 재시도, 데스크톱·모바일·다크모드.
- 최종 게이트: `pnpm lint`, `pnpm exec tsc --noEmit`, `pnpm test`, `pnpm test:db`, `pnpm build`, `pnpm e2e`. DB/E2E는 로컬 Supabase에서 수행한다.
- 돈 계산·큐 검증에는 결정적인 테스트 데이터를 쓴다. 실제 로컬 GPT의 문장 생성은 별도 smoke check로 검증하며 자동 테스트가 실제 모델 응답에 의존하지 않게 한다.

## 12. 구현/배포 경계

문서 승인 후에만 실행 플랜을 작성한다. 구현 순서는 통합 읽기 모델/화면과 리디렉션 → 예산 스냅샷·검증기 → 가구 격리 큐/워커 → 추천 UI와 안전한 저장 → 통합/E2E 검증이다.

배포는 후속 승인 범위다. 실제 적용 시에는 비파괴적 DB 추가 → 두 작업을 지원하는 Mac 워커 → 기능을 노출하는 웹 순서로 호환성을 검증한다. 예산 기능 지원 여부를 확인하지 못한 구 워커를 “준비됨”으로 표시하지 않는다. 기능을 내리더라도 기존 수동 예산과 내역 AI 진단이 계속 작동해야 한다.

이번 설계에서 제외: AI 자동 저장, 거래 자동 수정/제외, 월 자동 마감, 계좌 잔액 기반 가용 현금 예측, 외부 상품/투자 추천, 새 로컬 모델 설치, 범용 AI 작업 플랫폼, 장기간 미래의 예산 자동 작성.
