# 가져오기 경험 개선 설계

- 대상: `finance-web`
- 기준 커밋: `517e38aac2de760120714ed3997f52a98b21c018`
- 작업 브랜치: `feat/import-experience`
- 상태: 대화에서 네 건의 방향 승인 완료. 이 문서는 구현 전 최종 검토용이다.

## 1. 목적과 범위

완료된 처리 기록 조회·상태 필터·개별/일괄 복원은 유지하면서 다음 네 건을 구현한다.

1. 카드사와 소유자에 맞는 기본 카드 선택.
2. 테마 설정을 아이콘 하나와 드롭다운으로 축소.
3. 농협카드 암호화 PDF 명세서 가져오기.
4. 실제 처리 단계를 보여주고 결과 확인까지 유지되는 업로드 팝업.

기존 재무 계산식, 거래 흐름, 분류 우선순위·신뢰도, 인박스 검토·반영 방식은 변경하지 않는다. 새로운 작업 서버, 작업 기록 테이블, 백그라운드 작업 재개 기능은 만들지 않는다. 운영 DB 마이그레이션은 계획하지 않는다.

## 2. 현재 코드에서 확인한 점

- `account-match.ts`는 소유자·카드사 후보가 정확히 하나일 때만 ID를 반환한다. 여러 장인 경우 화면과 서버 모두 업로드를 막는다.
- `upload-action.ts`는 전달된 `accountId`를 사용하지 않고 자동 매칭을 다시 실행한다. 드롭다운만 바꾸어서는 선택이 반영되지 않는다.
- `theme-selector.tsx`는 라이트·다크·시스템 버튼 세 개를 항상 렌더링한다. 설정 저장, 시스템 연동, 차트 알림은 이미 구현돼 있다.
- 카드 업로드는 XLS/XLSX와 현대 HTML만 받는다. 농협 엑셀의 금액 열은 청구원금이다.
- `ActiveUploadProgress`는 실제 작업 이벤트 없이 타이머로 단계를 바꾸며 5.8초 뒤 100%를 표시한다.
- 뱅크샐러드는 `useFormStatus`, 카드는 컴포넌트의 `uploading` 상태에 팝업 수명을 맡긴다. 팝업은 페이지 애니메이션 내부에 렌더링된다. 팝업 조기 소멸의 정확한 발생 경로는 아직 재현으로 확정하지 않았다.

## 3. 기본 카드 선택

### 사용자 동작

- 선택한 카드사와 소유자에 속하는 활성 카드만 후보로 보여준다.
- 후보 1개: 자동 선택하며 다른 소유자·카드사의 카드로 변경할 수 없다.
- 후보 2개 이상: `기본 카드를 선택해 주세요`를 표시하고 직접 선택하기 전까지 업로드를 막는다. 첫 후보를 임의로 선택하지 않는다.
- 후보 없음: 안내와 결제수단 관리 링크를 제공한다.
- 카드사 또는 소유자가 바뀌면 후보를 다시 계산하고, 이전 선택이 유효하지 않으면 해제한다.
- 선택한 기본 카드는 이번 파일에서 생성하는 인박스 항목에 적용한다. 업로드 전에 이 적용 범위를 설명하고, 업로드 후에는 기존 인박스에서 건별 수정할 수 있다.
- 명세서 내 여러 카드의 자동 분리·행별 카드명 추론은 이번 범위에 포함하지 않는다.

### 서버 경계

클라이언트는 `accountId`를 전송한다. 서버는 양의 정수인지 검사하고 인증된 가구의 활성 카드 후보 중 소유자와 카드사가 일치하는지 다시 검사한다. 다른 가구·소유자·카드사, 비활성 카드, 계좌 유형, 존재하지 않는 ID는 쓰기 전에 거부한다.

명시적인 ID가 없고 후보가 하나인 기존 호출은 자동 매칭을 허용한다. 명시적인 잘못된 ID를 올바른 카드로 몰래 대체하지 않는다. 후보가 여러 장이고 ID가 없으면 선택 요청 오류를 반환한다.

카드 후보를 찾는 순수 함수를 화면과 서버에서 공유한다. 기존 지문을 일괄 재발급하거나 기존 거래의 결제수단을 수정하지 않는다.

## 4. 테마 아이콘·드롭다운

- 헤더에는 현재 선택 모드를 나타내는 작은 아이콘 버튼 하나를 표시한다.
- 버튼에 `화면 테마: 시스템`처럼 접근 가능한 이름을 제공한다.
- 메뉴에는 라이트·다크·시스템과 현재 선택 체크 표시를 제공한다.
- 선택 즉시 적용하고 메뉴를 닫는다. Escape와 바깥 클릭으로 닫으며, 키보드로 열기·이동·선택할 수 있다. 닫을 때 포커스를 적절한 트리거로 돌린다.
- 모바일에서도 동일한 세 옵션을 사용할 수 있게 한다. 모바일 더보기 메뉴와 겹쳐 잘리거나 가로 스크롤을 만들지 않는다.
- 기존 테마 저장 키, 시스템 변경 구독, 초기 테마 적용, 차트 갱신 이벤트를 재사용한다. 새 색 팔레트나 새로운 테마 상태 저장소는 만들지 않는다.
- 저장소 접근이 차단된 브라우저에서도 현재 화면에서 전환할 수 있어야 한다.

## 5. 농협 암호화 PDF

### 입력과 파싱

- 농협카드 선택 시 기존 XLS/XLSX에 PDF를 추가한다. 기존 파일당 2MB 제한은 유지한다.
- 파일 확장자와 PDF 헤더를 함께 확인한다. 다른 카드사의 PDF는 지원하지 않는 형식으로 명확히 거부한다.
- 현대 보안 HTML과 농협 PDF에 비밀번호 입력을 제공한다. 암호화되지 않은 파일에는 빈 비밀번호를 허용한다.
- 서버 Node 런타임에서 PDF.js를 이용해 복호화 및 텍스트 추출을 수행한다. 실제 채택 버전은 현재 Node·Next 빌드와 암호화 샘플 검증을 통과한 정확한 버전으로 고정한다.
- 페이지별 텍스트 좌표로 거래 행과 열을 구분한다. 줄바꿈된 가맹점, 여러 페이지와 반복 헤더를 처리한다.
- 이용일, 가맹점, 청구원금, 제공되는 결제수단 텍스트를 기존 `CardRow` 형태로 변환한다. 엑셀과 동일한 청구원금 기준을 유지하고 음수 금액의 부호를 보존한다.
- 명세서 제목의 청구월을 모든 거래의 이용월로 대체하지 않는다. 연도 보완은 명세서에 명시된 기간으로만 수행하며 날짜를 확정할 수 없으면 오류로 반환한다.
- 합계·소계·안내·혜택 요약은 거래로 만들지 않는다. 이미지 스캔본처럼 텍스트 거래를 읽을 수 없는 파일은 성공 0건으로 처리하지 않는다.
- 거래 표를 찾았지만 거래로 보이는 행의 날짜나 금액을 해석하지 못하면 전체 가져오기를 중단하고 형식 오류를 알린다. 읽을 수 있는 일부 행만 조용히 저장하지 않는다.

### 보안과 오류

- PDF는 텍스트 추출만 수행한다. 포함된 스크립트·첨부파일을 실행하지 않고 외부 리소스를 요청하지 않는다.
- 원본 파일과 비밀번호를 DB, 로그, 브라우저 저장소, 저장소 테스트 픽스처에 저장하지 않는다. 기존 분류기에 전달하는 거래 필드 외에 원본 PDF나 비밀번호를 AI로 전송하지 않는다.
- 실제 샘플은 로컬 수동 검증에만 사용한다. 커밋할 테스트는 합성 거래와 합성 비밀번호로 만든다.
- 비밀번호 누락·오류는 재입력 가능한 오류로 구분한다. 파일과 카드 선택은 유지하고 비밀번호만 다시 입력받는다.
- 손상된 파일, 지원하지 않는 레이아웃, 텍스트 없는 파일은 각각 이해 가능한 메시지를 제공한다. 파서 내부 오류나 원문을 응답에 노출하지 않는다.
- 파싱이 끝나면 기존 지문·중복 확인·추천·인박스 저장 흐름에 연결한다. PDF 업로드가 거래 원장에 바로 반영되지는 않는다.

## 6. 업로드 진행 상태

### 접근 방식

단순한 무기한 로딩 표시는 구현량은 작지만 현재 작업을 알려주지 못한다. 별도 작업 테이블과 폴링은 페이지를 닫은 뒤의 재개에 유리하지만 이번 요구에는 범위가 크다. 승인된 방식은 하나의 업로드 요청 안에서 실제 단계 이벤트를 스트리밍하는 것이다.

기존 업로드 업무 함수를 서버 전용 서비스로 분리하고, 서버 액션은 호환 어댑터로 유지한다. 새로운 POST Route Handler와 기존 액션은 같은 서비스를 사용한다. 인증된 가구 컨텍스트와 진행 이벤트 콜백을 서비스에 전달하며, 로직을 두 벌로 복사하지 않는다.

### 전송 계약

- Route Handler는 처리 시작 전에 인증, 동일 출처 요청 여부, 파일 개수·크기·형식, 카드 선택을 검증한다. 브라우저에서 받은 `householdId`는 사용하지 않는다.
- 한 요청의 응답으로 줄 단위 JSON 이벤트를 보낸다. 이벤트 종류는 `stage`, `heartbeat`, `result`, `error`다.
- 단계 이름은 `validating`, `reading`, `matching`, `classifying`, `saving`, `finalizing`이다. 실제 작업 진입 시에만 해당 이벤트를 보낸다.
- `stage`에는 선택적으로 실제 `completed`와 `total` 건수를 포함한다. 이 두 값이 없는 작업은 처리 중 표시를 사용한다. 전체 시간이 얼마나 지났는지로 작업 완료율을 추정하지 않는다.
- `heartbeat`는 연결이 유지됨을 나타낼 뿐 단계나 완료 건수를 증가시키지 않는다.
- `result`는 인박스 저장, 중복 표시 재계산, 선택한 자산 반영과 캐시 갱신이 정상 종료된 뒤 한 번만 보낸다.
- `error`는 안전한 오류 코드와 사용자 메시지만 포함한다. 비밀번호 오류, 잘못된 입력, 처리 오류를 구분한다.
- 스트림이 끝났다는 사실만으로 성공으로 간주하지 않는다. `result` 없이 연결이 닫히면 완료를 확인하지 못한 상태로 표시한다.

### 팝업 수명과 화면

- 업로드 유형에 상관없이 하나의 클라이언트 상태 모델을 사용한다: 대기 → 처리 중 → 완료 또는 오류.
- 모달은 페이지 애니메이션·폼 내부 렌더링 수명과 분리한다. 완료 후 데이터 재조회가 모달을 닫거나 결과를 지우지 않도록 한다.
- 서버가 받기 전에는 `파일 전송 중`, 받은 뒤에는 실제 단계와 가능한 경우 건수를 표시한다. 임의의 전체 백분율은 표시하지 않는다.
- 처리 중에는 모달을 임의로 닫거나 업로드 유형을 바꾸거나 다시 제출할 수 없다. 포커스를 모달 안에 유지하고 배경 조작을 막는다.
- 정상 완료 시 추가·기처리·자동 분류·검토 필요 건수를 표시하고 사용자가 `닫기` 또는 `검토 대기 보기`를 선택할 때까지 유지한다.
- 오류도 자동으로 사라지지 않는다. 재입력이 가능한 오류에서는 입력으로 돌아갈 수 있게 하며 파일과 카드 선택을 보존한다.
- 연결 오류는 저장이 전혀 없었다고 단정하지 않는다. 현재 인박스를 확인하도록 안내하며 자동 재업로드하지 않는다. 기존 지문 기반 재업로드 방어를 유지한다.
- 브라우저 닫기나 새로고침 뒤 작업의 지속·재개를 보장하지 않는다. 필요하면 브라우저 이탈 경고를 제공하되 백그라운드 작업처럼 안내하지 않는다.
- 처리 중 팝업 조기 소멸은 느린 요청, 화면 재조회, 업로드 탭 전환 조건으로 먼저 재현하고 회귀 테스트를 만든 뒤 원인에 맞춰 수정한다.

새로운 범용 repository, 이벤트 버스, 전역 앱 상태 프레임워크는 도입하지 않는다. 업로드 흐름을 관찰하는 데 필요한 좁은 변경만 분류 함수에 허용하며 분류 결과 자체는 바꾸지 않는다.

## 8. 검증과 출시 조건

- 카드 후보 0/1/여러 개, 후보 변경, 잘못된 ID와 다른 가구·소유자·카드사·비활성 카드 차단을 테스트한다.
- 선택한 카드가 모든 생성 인박스 행에 반영되는지 검증한다. 기존 파일 재업로드, 음수 금액, 같은 행의 발생 순번, 이전 지문 호환 동작을 회귀 검증한다.
- 기존 카드 지문에는 결제수단 ID가 없다. 서로 다른 카드의 동일 날짜·금액·가맹점 행을 완전히 구별한다고 주장하지 않는다. 이 변경에서 지문 정책을 임의로 바꾸지 않으며, 실제 검증에서 관련 누락이 확인되면 별도 데이터 정책 변경으로 보고한다.
- NH 합성 샘플로 암호 없음/정상/잘못된 암호, 다중 페이지, 줄바꿈 가맹점, 음수 금액, 합계 제외, 잘못된 날짜·손상·텍스트 없음·부분 파싱 거부를 테스트한다.
- 사용자 제공 PDF의 거래 행과 금액은 로컬에서 원문과 대조한다. 실제 금융 데이터는 커밋·테스트 로그에 남기지 않는다.
- 스트림의 정상 이벤트, 분할된 JSON 청크, 인증·출처 거부, 결과 없는 종료, 서버 오류, 느린 분류·저장과 중복 클릭을 테스트한다.
- E2E에서 느린 업로드 동안 모달 유지, 결과의 수동 닫기, 비밀번호 재입력, 업로드 후 검토 대기 갱신과 전체 화면 깜빡임 방지를 확인한다.
- 테마의 마우스·키보드·모바일 동작, 새로고침 후 유지, 시스템 변경, 차트 변경, 저장소 거부 상태를 검증한다.
- 390px 모바일과 데스크톱에서 폼 정렬, 모달 위치, 메뉴 잘림, 수평 스크롤을 확인한다.
- 각 기능 커밋 전 `pnpm lint`, `pnpm exec tsc --noEmit`, `pnpm test:all`, `pnpm e2e`, `pnpm build`를 검증한다. E2E와 DB 테스트, E2E와 빌드는 동시에 실행하지 않는다.
- 테스트 DB는 로컬 복사본만 사용한다. 운영 DB에 샘플을 업로드하지 않는다.
- 순서: 카드 선택 → 테마 메뉴 → NH PDF → 진행 상태 통합 → 전체 회귀 검증. 기능별 커밋 후 사용자 요청에 따라 푸시하며 운영 배포 여부는 실제 결과를 확인해 보고한다.
