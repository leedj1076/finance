# 공통 AI 진단 설정과 프롬프트 편집

작성일: 2026-09-10
코드 확인 기준: `main` / `4b1c54e` (애플리케이션 코드 기준 `275442c`)
상태: 공통·내역·예산 지침 편집, 기본값 복원, 프롬프트 미리보기, 실행 정보 조회라는 방향은 사용자 승인 완료. 아래 세부 명세의 문서 확인 단계이며 구현·운영 DB·배포는 아직 하지 않는다.

관련 명세: `docs/superpowers/specs/2026-09-10-ai-budget-planning-design.md`.

## 1. 목적과 범위

설정 한 곳에서 “우리집 AI가 무엇을 중요하게 보고 어떻게 설명할지”를 관리한다. 내역 진단과 예산 추천의 분석 지침은 편집할 수 있지만 금액 계산·가구 격리·근거 검증·결과 형식·실행 권한은 바꾸지 않는다.

승인된 구성:

- 공통 지침: 우리집 상황, 중점 분석 항목, 말투와 설명 분량.
- 내역 진단 지침: 지출 변화·이상 지출·전월 비교·다음 달 행동을 해석하는 관점.
- 예산 추천 지침: 예외 지출·유지할 비용·줄일 항목·추천 이유에 대한 관점.
- 편집 도구: 저장, 기본값 복원, 전달할 프롬프트 미리보기.
- 실행 정보: 로컬 Mac 워커 연결·지원 여부와 설정된 모델·실행 제한 조회.

설정은 로그인 개인이 아닌 **가구 공유**다. DJ/YJ가 같은 기준을 사용하며 다른 창의 수정을 조용히 덮어쓰지 않는다. 웹에서 모델, CLI 경로, 토큰, 타임아웃을 변경하거나 워커를 재시작하는 기능은 이번 범위에 없다.

AI 설정을 저장해도 진단을 자동 실행하거나 기존 보고서를 다시 쓰지 않는다. 기존 보고서와 저장된 예산은 유지하고 새로운 요청부터 새 지침을 사용한다.

## 2. 현재 코드와 선택한 접근

현재 `src/features/diagnosis/prompt.ts`의 `buildDiagnosisPrompt(snapshot)`에 실행 제한·보고서 형식·분석 지침이 한 문자열로 들어 있다. 워커가 실행 시점에 이 함수를 호출하므로 작업 생성 당시의 프롬프트는 별도로 기록되지 않는다.

실행 정보는 `src/features/diagnosis/worker.ts`의 보호된 로컬 설정에 있다. `diagnosis_workers`에는 현재 모델/프롬프트 지원 버전이 저장되지 않는다. 내역 큐 생성/조회 서비스의 실제 위치는 `src/features/diagnosis/queries.ts`이며 `service.ts`가 아니다.

설정 화면은 `src/app/settings/page.tsx`, 내비게이션은 `src/components/settings-nav.tsx`다. 기존 계정·결제수단·자산·정기거래·분류 규칙 설정을 유지하며 AI 진단 항목을 추가한다.

검토한 접근:

1. 전체 프롬프트 원문 교체: 유연하지만 출력 스키마와 안전 조건까지 지우기 쉬워 채택하지 않는다.
2. **공통/기능별 분석 지침 편집 + 고정 실행 계약 — 선택**: 분석 관점은 바꾸면서 기존 결과 UI와 검증을 유지한다.
3. 추가 문장만 입력: 간단하지만 기본 분석 지침 자체를 조정할 수 없어 요구보다 제한적이다.

## 3. 화면과 편집 동작

### 3.1 설정 페이지

주소는 `/settings?section=ai`, 메뉴명은 `AI 진단`이다. 화면은 다음 순서다.

1. 로컬 실행 상태와 읽기 전용 실행 정보.
2. 공통 분석 지침.
3. 내역 진단 지침.
4. 예산 추천 지침.
5. 프롬프트 미리보기와 변경사항 저장.

각 지침에는 `기본값 사용 / 사용자 지정` 상태, 현재 유효한 본문, 글자 수, 해당 영역의 기본값 복원 버튼을 둔다. 공통 최대 4,000자, 내역/예산 각각 최대 6,000자다. 프롬프트 자체가 계좌번호·비밀키 저장소가 아님을 안내한다.

- 기본값은 새 설정 모듈의 버전 관리된 문자열이다. 기존 내역 프롬프트의 분석 관점을 옮기되 계산/증거/형식 계약은 고정 영역으로 분리한다.
- `null`은 기본값 사용, 사용자 지정 빈 문자열은 추가 분석 지침 없음이다. 빈 문자열을 몰래 기본값으로 바꾸지 않는다. 고정 보고서 형식은 어느 경우에도 남는다.
- 복원은 해당 입력의 편집안만 바꾼다. 저장 전에는 DB·다른 영역·대기 작업이 바뀌지 않는다.
- 저장은 세 영역의 편집안을 한 번에 원자적으로 저장한다. 마지막 저장 시각을 표시하고 수정하지 않은 동일 내용 저장은 revision을 올리지 않는다.
- 저장 중에는 중복 제출을 막고 결과를 인라인으로 알린다. 전체 페이지를 다시 마운트하거나 입력/스크롤/펼침 상태를 초기화하지 않는다.
- 다른 창에서 먼저 저장했다면 충돌로 알리고 현재 서버값과 내 편집안을 비교할 수 있게 한다. 실패 시 내 편집안은 유지한다.
- 설정은 당월만의 특이사항을 적는 곳이 아니다. 여행·경조사 등 일시적 조건과 확정 추가 지출은 예산 화면의 해당 월 입력에 둔다.

내역/예산 진단 화면에는 `AI 진단 설정` 링크를 제공한다. 전역 설정 편집기를 각 화면에 중복 배치하지 않는다.

### 3.2 프롬프트 미리보기

미리보기는 서버의 실제 프롬프트 조합 함수를 사용한다. 진단 종류와 월을 선택하면 해당 가구의 그 시점 데이터로 최종 텍스트를 구성하되 **작업 생성·AI 실행·설정 저장은 하지 않는다**.

- 구분해 보여줄 영역: 고정 실행/출력 계약, 공통 지침, 해당 기능 지침, 분석 데이터.
- 고정 영역은 읽기 전용이다. 데이터 영역은 기본적으로 접어 두고 사용자가 펼치면 실제 전달될 JSON을 확인한다.
- 미저장 지침을 미리볼 수 있지만 `미저장 편집안 기준 · 진단 요청에는 저장된 설정이 사용됩니다`라고 명시한다.
- 예산 미리보기의 당월 특이사항/예정 지출은 기본적으로 비어 있음을 밝힌다. 실제 예산 요청에 넣은 특이사항까지 확인하려면 해당 작업의 프롬프트를 연다.
- 데이터 부족/미지원 월은 진단 생성과 같은 제한을 설명한다. 예산 기능 미배포 시 편집은 가능하되 실제 데이터 미리보기에는 기능 준비 중을 표시한다.
- 미리보기 후 거래나 설정이 바뀌면 실제 요청 내용이 달라질 수 있음을 명시한다. 미리보기 내용을 다음 요청에 몰래 고정하지 않는다.
- 미리보기는 분석 자료의 읽기 함수를 직접 사용한다. 기존 작업 상태 조회의 lease 만료 정리 같은 쓰기 부수 효과까지 실행하지 않는다.
- 대기·실행·완료 작업의 `사용한 프롬프트`는 그 작업에 저장된 지침과 스냅샷으로 복원한다. 이 조회는 현재 설정과 무관하다.
- 텍스트만 렌더링하고 HTML/Markdown의 실행 가능한 내용을 해석하지 않는다. 미리보기 응답은 가구 인증·크기 제한·private/no-store를 적용한다.

## 4. 프롬프트 조합과 안전 경계

개념적 순서는 고정 실행 계약 → 편집 가능한 공통/기능별 지침 → 고정 수치/근거/결과 계약 → 불변 분석 데이터다. 편집 내용은 명확하게 구분된 데이터로 직렬화하며 템플릿 코드나 명령으로 평가하지 않는다.

충돌 시 고정 계약을 우선하고, 분석 관점 안에서는 기능별 지침이 공통 지침을 구체화한다. 예산의 이번 달 입력은 그 요청에 한정된 사용자 정보이지 계산식이나 전역 지침을 수정하는 명령이 아니다.

고정할 항목:

- 실제 수입·지출·저축률·상한·예측·정기거래 계산과 이미 코드가 계산한 합계.
- 자료가 없는 달/진행 중인 달/미마감 자료의 해석, 환불 부호, 저축 납입 이중계상 금지.
- 예산 추천 하한, 상한 초과 사유, 알려진 카테고리와 근거 ID 검증.
- 존재하지 않는 거래·계좌 잔액·외부 통계를 사실처럼 만들지 않는 규칙.
- 필수 JSON 필드, 스키마 버전, 문장/리스트/금액 범위. 말투·분량 지침은 이 형식 안에서만 작동한다.
- 파일·셸·웹·MCP·외부 전송 등 도구 금지, 실행 환경 allowlist, 프로세스 타임아웃과 출력 한도.

문구로 고정 계약을 강조하는 것만 보안 장치로 삼지 않는다. 기존 실행부의 도구 차단·프로세스 제한과 서버 결과/근거/금액 검증이 독립적으로 계속 적용된다. 사용자 지침에 “검증 무시” 또는 닫는 태그가 들어가도 실행 권한이나 DB 저장 조건은 바뀌지 않아야 한다.

프롬프트 편집은 AI에게 직접 금액·목표를 설정하는 기능이 아니다. 예를 들어 지침에 “목표 40%”라고 써도 기존 저축 목표 설정은 바뀌지 않고 저장된 정본 목표를 사용한다. 충돌할 수 있다는 안내를 편집기 주변에 둔다.

공통/기능 지침에 적힌 가족 상황도 거래로 검증한 사실과 구분해 `설정에서 제공한 정보`로 표시한다. 예산 보고서가 이를 근거로 인용할 때는 요청 당시 공통/예산 지침의 영역과 짧은 원문 인용을 참조로 사용하고 서버가 실제 포함 여부를 검증한다. 현재 설정을 다시 조회해 과거 근거를 검증하지 않는다. 내역 보고서는 기존 JSON 구조를 유지하고 문장 안에서 사용자 제공 정보임을 밝힌다.

## 5. 설정 저장과 작업별 보존

### 5.1 현재 설정

`ai_diagnosis_settings`를 가구당 한 행으로 둔다.

- `household_id` 기본키/가구 FK.
- `common_instructions`, `ledger_instructions`, `budget_instructions`: nullable text.
- `revision`: 증가하는 정수. 행이 없는 초기 상태는 논리적 revision 0이다.
- `updated_at`, `updated_by`: 서버가 기록한다. 클라이언트가 작성자를 지정하지 못한다.

추가 설정 항목을 불특정 JSON 객체에 받거나 워커 비밀을 이 테이블에 복사하지 않는다. 조회는 없으면 기본값을 반환하고 데이터를 생성하지 않는다. 저장은 기대 revision을 비교하며 최초 동시 저장도 고유키 충돌로 감지한다. 복원도 같은 저장 경로를 쓴다.

이 테이블은 RLS를 켜고 가구 구성원에게 자기 행 SELECT만 허용한다. 쓰기는 인증된 서버의 검증된 설정 저장 경로로 한정한다. 모든 서버 쿼리는 별도로 householdId를 제한한다.

### 5.2 요청 시점의 불변 입력

두 종류의 작업에 nullable `prompt_input`을 추가한다. 기존 내역 작업/스냅샷/결과 버전은 재작성하지 않는다. 새 작업은 설정 읽기·분석 자료 읽기·prompt_input 생성·큐 저장을 일관된 트랜잭션으로 묶는다.

`prompt_input`에는 다음을 보관한다.

- 프로토콜 버전, 진단 종류, 설정 revision, 기본/고정 프롬프트 버전.
- 해당 요청에 실제 사용한 공통/기능별 지침의 유효 본문과 기본값/사용자 지정 출처.
- 서버가 조합한 데이터 앞/뒤 고정 텍스트와 전체 프롬프트 해시.
- 해당 진단 종류의 유효 지침 해시. 공통+그 기능의 지침+기본/고정 버전만 포함하고 다른 기능 지침은 제외한다.

분석 데이터는 기존 snapshot에 한 번만 저장한다. 앞/뒤 텍스트와 정렬된 키의 결정적 JSON 직렬화를 사용해 워커·미리보기·과거 조회가 같은 최종 프롬프트와 해시를 만들게 한다. 구형 `prompt_input=null` 경로는 기존 직렬화/실행 동작을 유지한다.

설정 API/미리보기 요청은 실제 읽은 본문 기준 128KiB로 제한한다. 직렬화한 prompt_input도 128KiB 이하, 예산 snapshot은 기존 1MiB 이하이며 합쳐진 claim 응답이 기존 2MiB 한도 안에 드는지 테스트한다. 모델 출력 한도와 근거 한도는 프롬프트 편집 때문에 늘리지 않는다. 너무 큰 입력은 자르지 말고 명확한 오류로 돌려준다.

prompt_input은 생성 후 수정할 수 없다. 워커가 시작할 때 현재 설정을 다시 읽지 않으며, 기본 문구 배포가 있어도 이미 요청한 작업의 문구를 교체하지 않는다. 서버의 작업 생성 경로가 고정 텍스트를 만들고, 브라우저가 prefix/suffix/hash/지원 버전을 지정하는 요청은 거부한다.

별도 전체 프롬프트 버전 관리 UI나 모든 설정 변경의 감사 이벤트 테이블은 만들지 않는다. 현재 설정 revision과 실제 실행된 작업의 불변 입력으로 이번 요구를 충족한다.

## 6. 기존 결과와 변경 알림

- 보고서의 데이터 변경 여부와 프롬프트 설정 변경 여부를 별도로 표시한다. 내역의 기존 `isStale` 계산식은 지침 revision으로 오염시키지 않는다.
- 지침만 바뀌었다면 `진단 지침이 변경되었습니다. 새 지침으로 다시 진단할 수 있습니다.`라고 안내한다. 이전 보고서는 계속 읽을 수 있다.
- 예산 지침 변경만으로 기존 추천의 계산 유효성·저장된 금액·출처를 무효화하지 않는다. 이전 지침 기반이라는 표시와 당시 지침을 보면서 명시적으로 선택 적용할 수 있다. 거래/목표/예산 충돌에 대한 기존 안전 검사는 그대로 적용한다.
- 공통 지침 변경은 두 종류에 영향을 준다. 예산 지침만 바꾸면 내역 진단에는 변경 알림을 띄우지 않는다. 동일 본문으로 복원하면 유효 해시가 같아지므로 불필요한 재진단 알림을 띄우지 않는다.
- 재진단은 사용자가 실행한다. 이전 보고서와 예산 편집안은 새 결과를 기다리는 동안 유지한다.
- 실행 당시 지침을 기록하지 않은 과거 결과에는 `이전 결과 · 사용한 프롬프트 미기록`이라고 표시한다. 현재 코드의 문구를 당시 실제 문구였던 것처럼 채워 넣지 않는다.
- 동일 요청의 네트워크 재시도는 원래 작업/지침을 유지한다. 설정을 수정한 뒤 다시 진단하려면 새 요청이다. 이미 활성 작업이 있으면 기존 작업의 상태를 보여주며 그 입력을 교체하지 않는다.

## 7. 워커 지원과 단계적 호환성

설정 페이지의 연결 정보는 워커가 인증된 heartbeat로 보고한 자료다. 브라우저가 임의의 경로나 명령을 워커에 전달하는 제어 채널은 만들지 않는다.

조회할 정보:

- 연결 상태, 마지막 확인 시각, 편집 지침 지원 여부, 예산 기능 지원 여부.
- 워커 설정의 모델명. 명시 모델이 없으면 `CLI 기본값`으로 표시하고 실제 선택된 모델을 추측하지 않는다.
- 적용되는 타임아웃(현재 기본 180초, 하드 상한 300초)과 도구 사용 금지 상태.

모델명은 제한된 식별 문자열로만 보고한다. 설정 파일 원문·경로·토큰·환경 변수·CLI 오류 본문은 전송하지 않는다. 여러 워커가 있으면 행별로 모델/지원 상태/마지막 확인을 보여주고 하나의 모델이 항상 실행된다고 오인시키지 않는다. 오프라인 정보에는 마지막 확인 기준임을 표시한다.

구형 워커가 새 지침을 무시하고 작업을 성공 처리하지 못하도록 **claim 단계에서 격리**한다.

- 기존 `claim_diagnosis_job(p_token)`은 같은 인자·반환 구조를 유지하되 `prompt_input IS NULL`인 기존 형식 작업만 가져오게 한다.
- 새 프롬프트 지원 claim RPC는 기존 snapshot과 prompt_input을 반환한다. 유효 토큰·가구·지원 프로토콜을 확인하고 legacy/new 내역 작업을 처리할 수 있다.
- 기존 내역 heartbeat/finish의 소유권·claim token·lease·결과 검증 계약은 유지한다. 별도 결과 형식이나 내역 큐를 하나 더 만들지 않는다.
- 예산 큐는 별도로 유지하되 prompt_input 지원 작업만 해당 버전의 워커에 전달한다. Mac 프로세스 하나가 내역/예산을 번갈아 처리하는 기존 예산 설계를 유지한다.
- 버전 있는 작업을 legacy 호출로 폴백하여 처리하지 않는다. 지원 워커가 없다면 설정 저장은 가능하지만 새 지침 실행은 연결/업데이트 안내와 함께 막는다. 구 웹이 만든 legacy 내역 작업은 계속 처리할 수 있다.
- 설정 프로토콜 heartbeat는 긴 작업 중에도 갱신한다. 예산 capability와 지침 capability는 별도 의미이며, 한쪽 지원만으로 다른 쪽까지 준비됨으로 표시하지 않는다.

이 호환 필터는 예산 명세의 “기존 claim RPC 그대로 유지” 원칙에 대한 최소 확장이다. 기존 함수 이름·인자·legacy 반환과 금융 계산은 유지하며, 신규 지침 작업을 구형 워커에게 넘기지 않는 선택 조건만 추가한다. 변경은 새 additive migration에 넣고 `0005_diagnosis_queue.sql` 자체는 수정하지 않는다.

배포 순서는 승인 후 DB 확장/legacy 필터 → 호환 워커 → 설정/예산 웹 기능이다. 롤백 시 신규 지침 작업을 legacy로 바꾸지 않고, 기존 결과/수동 기능을 보존하면서 지원 워커를 다시 연결하도록 안내한다.

## 8. 구성 경계와 예산 계획 연결

`src/features/ai-settings/`가 기본값·지침 조합·설정 검증/읽기/저장·설정 편집 UI를 담당한다. 계정 비밀번호 변경과 별도 경계를 유지한다. 파일 세분화와 정확한 인터페이스는 실행 계획에서 정한다.

`src/features/diagnosis/`와 새 `budget-recommendations/`는 각자의 분석 자료·고정 출력 스키마·결과 검증을 소유한다. 공용 모듈이 모든 도메인 계산을 대신하지 않는다. 서버가 가구 설정을 넣어 작업 입력을 만들고, 워커는 불변 입력으로만 실행한다.

이 기능은 예산 화면 통합과 별도로 검증할 수 있지만, 예산 생성/워커 계약과 접점이 있다. 기존 11-task 예산 초안을 그대로 실행하지 말고 다음 순서로 업데이트한다.

1. 기존 예산 화면 통합은 유지한다.
2. 공통 설정 저장/프롬프트 조합과 내역 진단 호환 경로를 독립 테스트 가능한 단위로 추가한다.
3. 예산 스냅샷/검증기/큐에서 prompt_input 계약을 소비한다.
4. 공용 실행부와 단일 워커는 한 번만 정리하고 양쪽 지침을 처리한다.
5. 설정 편집·미리보기·내역 알림과 예산 선택 적용 UI를 연결한다.
6. 두 기능의 데이터 격리·과거 결과·동시 수정·브라우저 회귀를 함께 검증한다.

기존 예산 플랜의 migration 번호는 아직 확정하지 않는다. 실행 순서와 현재 journal을 확인해 연속된 신규 migration으로 배치하며 운영 DB에는 이 설계 단계에서 적용하지 않는다.

## 9. 검증 기준

- 설정: 기본값/빈 문자열/null 구분, 길이·본문 바이트 한도, 동일 저장 no-op, 최초 저장/동시 수정 충돌, 복원 후 저장, 다른 가구 접근과 작성자 위조 거부.
- 조합: 공통/기능별 분리, 기능별 유효 해시, 고정 계약 유지, 악성 태그/역할 지시/JSON 문자열이 코드·CLI 옵션으로 해석되지 않음.
- 보존: 설정 A로 요청 → 설정 B 저장 → 워커가 A로 실행; 기본 프롬프트 코드 변경 뒤에도 기존 작업 프롬프트 동일; 재시도 동일 입력; 신규 요청만 B 사용.
- 검증: 미리보기·저장된 작업·워커가 구성한 전체 텍스트 해시 일치, 알 수 없는 프로토콜/잘못된 해시 거부, 출력/근거/금액 검증 우회 불가.
- 호환: old claim이 prompt_input 작업을 받지 않음, 새 워커의 legacy 처리, 잘못된 가구/취소 토큰/lease 처리, 긴 작업 중 capability liveness, 모델 비공개 정보 미노출.
- 변경 알림: 설정 변경과 거래 변경을 구분; 예산 전용 변경이 내역에 영향 없음; 지침 수정만으로 저장 예산 무효화 없음; 미기록 legacy 프롬프트를 위조하지 않음.
- E2E: 설정 진입·수정·미리보기(no queue)·저장·재접속, 다른 창 충돌, 두 진단의 새 지침 사용, 진행 중 작업 보존, 기존 보고서 유지, 읽기 전용 모델, 모바일·다크·키보드·인라인 저장.
- 최종 게이트: `pnpm lint`, `pnpm exec tsc --noEmit`, `pnpm test`, `pnpm test:db`, `pnpm build`, `pnpm e2e`. DB/E2E는 로컬 Supabase에서 수행하며 모델 응답은 결정적 fixture로 대체한다. 실제 CLI 생성은 별도 synthetic-data smoke로 보고한다.

## 10. 범위 밖과 승인 경계

범위 밖: 웹 모델 선택/타임아웃 편집, 키/워커 경로 편집, 원격 셸·워커 재시작, 외부 프롬프트 마켓, 임의 템플릿 코드, 새로운 AI 공급자, 보고서 출력 스키마 편집, 프롬프트 수정에 따른 자동 재진단·자동 예산 저장, 전체 설정 변경 이력 UI.

대화 승인 내용을 이 명세로 구체화했다. 문서 확인 후 `writing-plans`로 예산 초안을 업데이트하고 실행 방법을 정한다. 구현 전 운영 DB 수정, push, 배포, production 워커 재시작은 하지 않는다. 다른 세션의 미추적 문서와 `outputs/`는 보존한다.
